# Arsitektur Sisa-Saji

Dokumen ini untuk developer yang mengubah kode. Cara menjalankan aplikasi ada di [README](../README.md), spesifikasi awal di [blueprint_sisa_saji.md](../blueprint_sisa_saji.md). Bila skema di kode berbeda dari DDL di blueprint, `src/db/schema.ts` yang berlaku; daftar perbedaannya ada di README.

## Aturan bisnis yang tidak boleh dilanggar

Aturan ini dijaga oleh kode dan test. Mengubah salah satunya berarti mengubah produk, bukan sekadar refactor.

- **Hanya ambil sendiri.** Tidak ada kurir, ongkir, atau `delivery_fee`. Pembeli mengambil pesanan di warung sebelum `pickup_end_time`. Margin warung yang tipis tidak menanggung biaya logistik. Opsi "Titip Antar Kolektif Kos/Asrama" di checkout hanya tampilan: berlabel "Segera hadir", tidak bisa dipilih, dan tidak ada field pengantaran di `CheckoutBody`, total, atau pesanan. Biaya rencananya (`COLLECTIVE_DELIVERY_FEE_DISPLAY_IDR`, Rp 2.500) tidak pernah ditagih. Tombol "Kabari saya" mencatat minat di `delivery_interests` (satu baris per akun, `GET/POST/DELETE /api/v1/delivery-interest`, `src/server/services/delivery-interest.ts`): pengunjung lain hanya melihat jumlahnya, nama kos/asrama hanya dikirim ke pemiliknya, dan akun demo ditolak (`DEMO_LOCKED`) serta tidak ikut dihitung.
- **Keranjang hanya untuk satu warung.** `src/stores/cart.ts` menolak menu dari warung lain sampai pembeli mengonfirmasi `DiffMerchantDialog`, lalu keranjang lama dikosongkan. Satu baris keranjang = satu menu dengan satu lauk (`lineKey(batch_id, lauk)`), jadi menu yang sama dengan dua lauk menjadi dua baris; persist versi 2 memigrasikan keranjang lama tanpa lauk.
- **Harga tidak pernah di bawah harga lantai.** Optimizer tidak boleh menurunkan `current_selling_price_idr` di bawah `menus.min_recovery_price_idr`, berapa pun sisa waktunya.
- **Stok dikunci secara atomik di PostgreSQL.** Checkout menjalankan satu `UPDATE` bersyarat dalam transaksi (`available_stock -= q`, `reserved_stock += q`, hanya jika `available_stock >= q`). TTL pembayaran 600 detik; bila lewat, worker mengembalikan stok. Invarian per batch: `initial_stock = available_stock + reserved_stock + sold`. Semua penguncian lewat `src/server/services/stock.ts`, jangan menulis versi sendiri.
- **Biaya layanan dibayar pembeli.** Pembeli membayar subtotal harga pemulihan + Rp 1.500 − voucher. Warung menerima subtotal penuh (`net_merchant_payout_idr = subtotal_recovery_idr`), voucher ditanggung platform. Pengecualian: tiket "bayar di warung" tidak membayar biaya layanan (`serviceFeeFor("BAYAR_DI_WARUNG")` = 0, karena platform tidak bisa menagih dari uang tunai) dan tidak menerima voucher (`VOUCHER_INVALID`). Sumber kebenaran: `src/lib/pricing/order-totals.ts`.
- **Fair use saat checkout** (`src/server/services/orders/checkout.ts`):
  - maksimal 1 pesanan belum dibayar per warung dan 2 secara total (tiket "bayar di warung" yang masih terbuka ikut dihitung);
  - checkout ulang dengan item sama mengembalikan pesanan yang sama (aman dari ketukan ganda);
  - porsi per pembeli per batch maksimal `max(3, ceil(initial_stock / 2))`;
  - 3 pesanan batal atau kedaluwarsa dalam 30 menit membuat checkout baru ditolak sementara (`RATE_LIMITED`); tiket yang dibatalkan warung karena stok habis tidak dihitung;
  - tiket "bayar di warung" paling banyak `PAY_AT_WARUNG_MAX_PORTIONS` (3) porsi di warung mana pun;
  - di warung uji coba saja, pembeli yang 2 kali tidak mengambil tiketnya di warung uji coba dalam 7 hari (kedaluwarsa, atau dibatalkan warung karena "Tidak datang") tidak bisa membuat tiket baru di sana dulu (`RATE_LIMITED`); tiket yang lewat di warung demo tidak membuang masakan siapa pun, jadi tidak dihitung;
  - akun demo pembeli dipakai banyak pengunjung sekaligus, jadi tiket "bayar di warung" miliknya tidak dihitung di batas pesanan terbuka (tiket yang masih terbuka) dan aturan 3 batal dalam 30 menit (tiket yang lewat). Satu pengunjung tidak bisa mengunci pengunjung lain. Batas porsi per batch tetap menghitung tiket terbukanya, supaya satu sesi demo tidak bisa menahan seluruh porsi sebuah batch.
- **Pesanan yang tidak diambil.** Pesanan `PAID` atau `READY_FOR_PICKUP` yang belum diambil sampai `pickup_deadline_at` + 30 menit diubah worker menjadi `EXPIRED`. Warung tetap menerima pembayaran tepat sekali, pembeli tidak mendapat kredit dampak (`closeUnclaimedOrders` di `src/server/services/orders/pickup.ts`). Tiket "bayar di warung" tidak mendapat kelonggaran 30 menit itu (lihat di bawah).
- **Bayar tunai di warung.** Di semua warung pembeli bisa memilih "Bayar Tunai di Warung" (`payment_method = BAYAR_DI_WARUNG`); warung uji coba hanya menerima cara ini. Checkout langsung membuat tiket `READY_FOR_PICKUP` tanpa QRIS, biaya layanan, atau voucher. Porsinya tetap dikunci (`reserved_stock`) sampai warung memverifikasi pengambilan (`commitReservation` saat itu, `paid_at` diisi, saldo dompet tidak ditambah karena uang sudah diterima tunai). Karena porsinya ditahan gratis, tiket hanya berlaku `PAY_AT_WARUNG_HOLD_MINUTES` (30) menit sejak checkout dan tidak pernah melewati akhir pengambilan batch; batas itu disimpan sebagai `pickup_deadline_at` tiket, sehingga tiket pembeli, antrean warung, dan layar scan menghitung mundur ke waktu yang sama (banner tiket pembeli memerah pada `CASH_HOLD_URGENT_MINUTES` terakhir). Tepat saat batas lewat (tanpa kelonggaran), tiket menjadi `EXPIRED` dan porsinya kembali ke stok: lewat job menit (`closeUnclaimedOrders`) dan juga langsung saat tiket dibaca, di-scan, atau saat ada checkout untuk batch yang sama (`expireLapsedHolds` jalan di setiap checkout, terbatas pada batch yang dipesan, `src/server/services/orders/hold.ts`), karena di Vercel job tidak jalan tiap menit. Warung bisa membatalkan tiket terbuka dari layar Pesanan (`POST /api/v1/merchant/orders/:id/cancel`): "Stok habis" kapan saja (melepas tiket dan membuat sisa stok menu itu 0 supaya tidak dipesan orang lain), "Tidak datang" baru mulai `noShowCancelOpensAt` (15 menit terakhir masa tahan, dan tidak sebelum separuhnya lewat; lebih awal = `409`), karena pembatalan itu dihitung sebagai tiket tidak diambil pembeli; porsinya kembali ke stok. Pembeli melihat tiketnya "Dibatalkan oleh warung" dengan alasan dalam kalimat untuk pembeli (`buyerCancelText`). Tiket yang dibatalkan atau tidak diambil melepas porsinya lewat `abandonPayAtWarungOrder` di `stock.ts`. Kartu "Pembayaran di warung" di tiket memilih teksnya dari `merchant.is_pilot` dan `merchant.is_demo_data` di detail pesanan (`isDemoData()` saat dibaca): teks uji coba beserta peringatan tidak datang, catatan "Warung ini data demo" untuk warung lain selama data demo, atau teks netral bila kedua field tidak ada (tiket dari cache offline). Implementasi: `orders/checkout.ts`, `orders/hold.ts`, `orders/pickup.ts`.
- **Uji coba lapangan terpisah dari data demo.** Warung yang bergabung dengan `PILOT_INVITE_CODE` (`merchants.is_pilot`) dibayar langsung di tempat: checkout selalu membuat tiket "bayar di warung" (lihat di atas), dan akun demo pembeli tidak bisa memesan di sana (`403 FORBIDDEN`). Hanya warung uji coba yang foto batch dan `menus.image_url`-nya tampil ke publik, dan hanya warung uji coba yang memicu Notifikasi Jam Lapar per acara. Bergabung ke uji coba ditolak untuk akun demo dan selama kode masuk masih tampil di layar (`isRealOtpDelivery()` salah); `GET /api/v1/merchant/pilot` memberi tahu kartu Pengaturan alasannya. `GET /api/v1/stats/pilot` (halaman `/uji-coba`) hanya menghitung pesanan `COMPLETED` di warung uji coba yang dibuat setelah warung bergabung, tanpa pesanan pemilik di warungnya sendiri. `topUpDemoBatches` melewati warung uji coba, dan `seedDatabase` menolak menghapus data uji coba tanpa `allowPilotWipe`. Implementasi: `src/server/services/merchant/pilot.ts`.
- **Penurunan sampah diukur terhadap angka awal yang tetap.** Saat bergabung, warung mengisi `pilot_baseline_leftover_portions` (perkiraan porsi yang biasanya **dibuang** per malam sebelum Sisa-Saji, bukan semua porsi sisa; nama kolom dipertahankan); angka ini hanya bisa diisi sekali. Kedua sisi perbandingan jadi sama-sama porsi dibuang. Setiap malam warung mencatat ke mana sisa yang tetap tidak laku pergi (`leftover_reports`: dibagikan, pakan ternak atau maggot, kompos, dibuang), untuk tadi malam atau malam ini saja. `/uji-coba` menghitung penurunan = 1 − dibuang ÷ (angka awal × malam laporan), hanya dari laporan sejak tanggal bergabung dan hanya dari warung yang mengisi angka awal. Angka awal dan laporan diisi sendiri oleh warung dan tidak diperiksa tim; `/uji-coba`, kartu laporan sisa, dan kartu uji coba di Pengaturan menyebutkan itu. Implementasi: `src/server/services/merchant/leftovers.ts`.
- **Kode OTP di layar tidak boleh membuka akun orang sungguhan.** Selama `OTP_DEV_MODE=true`, siapa pun yang tahu nomor HP atau email seseorang bisa melihat kodenya. Karena itu `requestOtp` dan `verifyOtp` menolak akun pemilik warung uji coba dan pembeli yang pernah memesan di warung uji coba (`403 FORBIDDEN`, `details.reason = "REAL_OTP_REQUIRED"`, `src/server/services/auth/real-accounts.ts`), dan bergabung ke uji coba ditolak selama `isRealOtpDelivery()` salah. Akun demo dan akun data demo tetap memakai kode di layar. Pesan penolakannya sengaja netral (tidak menyebut warung uji coba) dan baru diberikan setelah batas permintaan per nomor dicek, supaya tidak bisa dipakai menebak siapa yang pernah memesan di warung uji coba. Sesi juga mencatat cara masuknya: JWT dari kode yang benar-benar terkirim membawa klaim `otp: "real"`, dan begitu `isRealOtpDelivery()` benar, `getSessionUser` menolak sesi tanpa klaim itu (kecuali akun demo), jadi akun yang diambil alih saat mode demo tidak terbawa setelah pengiriman asli dinyalakan. Dengan pengiriman asli, `requestOtp` juga membatasi per perangkat (`otp_codes.client_key` = hash IP) dan per jam untuk seluruh aplikasi, dan menolak nomor/email akun demo (`details.reason = "DEMO_LOGIN_ONLY"`).
- **Akun demo bersama dikunci.** Akun demo pembeli dan warung (`isDemoAccount`, `src/lib/demo-accounts.ts`) dibuka siapa saja lewat tombol "Masuk dengan akun demo", jadi `assertDemoUnlocked` (`src/server/auth/session.ts`) menolak perubahan nama/profil (`PATCH /profile`), profil warung, rekening, jam, buka/tutup (`PATCH /merchant/me`), menu (`POST /merchant/menus`, `PATCH /merchant/menus/:id`), pendaftaran warung (`POST /merchant/onboarding`), uji coba (`/merchant/pilot`), dan daftar tunggu titip antar (`POST /delivery-interest`) dengan `403 FORBIDDEN`, `details.reason = "DEMO_LOCKED"`. Login OTP sebagai mitra juga tidak mengubah peran akun demo pembeli. Alur demo tetap terbuka: publikasi dan pembatalan surplus (paling banyak `DEMO_MAX_BATCH_STOCK` = 30 porsi per batch), lauk malam ini dan janji porsi (`PATCH /merchant/surplus/:id`), foto batch (hanya terlihat oleh sesi akun demo dan pemiliknya selama 60 menit, lihat Foto batch), pesanan, verifikasi pengambilan, dan ulasan. Isi porsi dan pilihan lauk di menu tetap terkunci karena itu edit menu. `SessionUser.is_demo` (`GET /api/v1/auth/me`) membuat UI menampilkan formulir terkunci dengan `DemoLockNotice` alih-alih formulir yang gagal saat disimpan.
- **Isi menu transparan.** Tidak ada lagi paket kejutan. Menu baru wajib mencantumkan minimal satu isi porsi atau lauk: `menus.contents` (selalu tampil, maks. `MENU_CONTENTS_MAX` = 12) dan `menus.lauk_options` (pembeli memilih satu, maks. `LAUK_OPTIONS_MAX` = 8), tiap item maks. 40 karakter, dirapikan dan tanpa duplikat (`src/lib/lauk.ts`). Kontrak dan layanan menu menolak kategori `MYSTERY_BAG` dan `is_mystery_bag = true`. Menu lama yang isinya masih kosong tetap bisa dipublikasikan (pembeli hanya melihat nama dan deskripsi), tetapi edit daftar tidak boleh membuat keduanya kosong. Migrasi `0009` menonaktifkan menu kejutan dan mengakhiri batch live-nya yang belum dipesan; publikasi menu kejutan ditolak (`details.reason = "MENU_CONTENTS_REQUIRED"`), discovery, peta, dan worker eskalasi (harga dan push "Diskon Kilat") menyaring barisnya, dan checkout menolak batch sisa menu kejutan (`BATCH_CLOSED`). Enum `MYSTERY_BAG` dan kolom `menus.is_mystery_bag` tetap ada untuk histori dan ML. Batch menyimpan lauk yang masih ada malam ini (`surplus_batches.lauk_available`, default semua lauk menu): harus bagian dari `lauk_options` dan menyisakan minimal satu bila menu punya lauk, dicek saat publikasi dan `PATCH` (hanya selama batch live). Saat warung mengubah `lauk_options` menu, `updateMenu` menyelaraskan batch live-nya dalam transaksi yang sama: lauk yang dihapus hilang, lauk baru (termasuk ejaan yang dibetulkan) ikut tersedia, lauk yang dimatikan malam ini tetap mati, dan bila tidak ada yang tersisa semua pilihan baru tersedia. Lauk tidak punya stok sendiri: porsi batch tetap satu-satunya unit yang dikunci, jadi `stock.ts` tidak berubah dan batas porsi per batch menjumlahkan semua baris lauk. Di checkout, `lauk` per baris opsional; bila dikirim harus ada di `lauk_available` (tanpa membedakan huruf besar-kecil, kalau tidak `VALIDATION_ERROR` dengan `lauk_available` di `details`) dan disimpan sebagai `order_items.lauk_choice` dengan ejaan batch. Menu yang sama dengan dua lauk menjadi dua baris `order_items` dalam satu reservasi.
- **Foto batch.** Warung bisa menambah satu "Foto etalase malam ini" per batch setelah publikasi (`POST`/`DELETE /api/v1/merchant/surplus/:batchId/photo`, body mentah `image/jpeg`). Akun demo boleh, karena ini bagian dari alur publikasi. Ponsel mitra mengecilkan foto ke sisi terpanjang `BATCH_PHOTO_MAX_EDGE_PX` (1280) dan target 250 KB, lalu menyandikannya ulang ke JPEG, yang sekaligus membuang EXIF dan GPS (`src/components/merchant/lib/compress-photo.ts`). Server hanya menerima JPEG (byte awal `FF D8 FF`, selain itu `415`), maks. `BATCH_PHOTO_MAX_BYTES` (400 KB, `413`), maks. 2560 px per sisi dan 4 MP (dibaca dari header frame SOFn), untuk batch milik sendiri yang masih live (`404`/`409`). Batasnya 5 unggahan per batch (`surplus_batches.photo_upload_count`, tidak kembali saat foto dihapus), 20 per warung per jam (`batch_photo_uploads`), dan 15 foto akun demo yang live sekaligus (`429 RATE_LIMITED`). Hitungannya dijalankan di bawah advisory lock transaksi (satu per warung, plus satu kunci bersama untuk unggahan demo), jadi unggahan paralel ke batch berbeda tidak bisa melewati batas. Byte disimpan di Postgres (`batch_photos.bytes`, `bytea`, satu baris per batch) dan hanya dibaca `GET /api/v1/batches/:batchId/photo?v=<versi>`; listing tidak pernah memilih kolom byte. Hak melihat dicek di setiap pembacaan (`canViewBatchPhoto`, `src/server/services/batch-photos.ts`) dari metadata saja, dan byte baru dibaca setelah diizinkan; batch harus masih live (`ACTIVE`/`SCHEDULED`/`SOLD_OUT`, sebelum `pickup_end_time`):
  - warung uji coba: semua orang, dengan badge "Foto asli etalase pukul 19.45 WIB" dan `Cache-Control: public, max-age=3600` (URL membawa `?v=`);
  - unggahan akun demo (`demo_only`): hanya sesi akun demo dan pemiliknya, selama `DEMO_BATCH_PHOTO_TTL_MINUTES` (60) menit, dengan badge "Foto contoh akun demo", tidak pernah "Foto asli";
  - warung lain (daftar sendiri atau seed): hanya pemiliknya, sebagai pratinjau.

  Selain foto warung uji coba, responsnya `private, no-store`. Semua penolakan berupa `404 "Foto tidak tersedia"`, supaya keberadaan foto tidak bisa ditebak; respons membawa `nosniff`, CSP `sandbox`, dan CORP `same-origin`. Karena berada di bawah `/api/`, service worker tidak pernah meng-cache-nya. Foto dihapus permanen saat batch dibatalkan atau kedaluwarsa, dan job menit (`purgeEndedBatchPhotos`) menghapus foto batch yang sudah berakhir serta foto demo yang lewat 60 menit. Badge foto hanya untuk foto unggahan batch itu, tidak pernah untuk seed, landing, tur, atau `menus.image_url`; `image_url` menu hanya dikirim ke pembeli untuk warung uji coba. Seed tidak membuat foto.
- **Sinyal kepercayaan hanya dari ulasan.** Ulasan punya dua pertanyaan opsional: kebersihan 1–5 (`reviews.hygiene_rating`) dan porsi sesuai porsi normal (`reviews.portion_full`). `reviewOrder` dan seed menulis agregatnya ke `merchants` (`hygiene_avg` tetap NULL sampai ada jawaban, `hygiene_count`, `portion_full_count`, `portion_answer_count`). Server mengirim `TrustSignals` (`toTrustSignals`, `src/lib/trust-signals.ts`) yang null sampai `TRUST_SIGNAL_MIN_REVIEWS` (10) ulasan menjawab pertanyaan itu, jadi satu ulasan tidak bisa menggeser angkanya. Teksnya menghitung ulasan, bukan pembeli: "Kebersihan 4,9/5 dari 42 ulasan", "Porsi normal 95% (kenyang) dari 40 ulasan", dan di bawah `PORTION_KENYANG_MIN_PCT` (90%) "Porsi pas menurut 70% ulasan". Angka 100% hanya muncul bila datanya 100%. `surplus_batches.full_portion` adalah pengakuan warung, bukan penilaian: bila dimatikan, pembeli melihat "Porsi lebih kecil"; selama ulasan belum cukup, chip porsi menulis "Janji porsi normal" (`portionChipText`). Rating bintang tampil sejak 1 ulasan; tanpa ulasan tertulis "Belum ada ulasan", tidak pernah "5,0 (0)".
- **Kode pickup tidak bisa ditebak beruntun.** Setelah 10 kode salah dalam 10 menit, input kode manual warung diblokir sementara (`RATE_LIMITED`). Pemindaian QR (token HMAC) tetap jalan.

## Data demo

- `CAMPUSES` (`src/lib/constants.ts`) berisi 21 kampus/kota. Tiga titik Bogor (`ipb`, `bogor`, `cibinong`) selalu paling atas, dan `CAMPUSES[0]` (IPB Dramaga) menjadi titik pencarian default. Helper ada di `src/lib/campuses.ts`.
- Seed membuat 95 warung fiktif (Bogor 28, DI Yogyakarta 15, sisanya dari Medan sampai Jayapura). Warung indeks 0 adalah warung demo, Warung Nasi Teh Euis. Di test, pakai `DEMO_MERCHANT_SLUG` dan `DEMO_MERCHANT_NAME`, jangan menulis slug langsung.

## Stack dan keputusan teknis

- **Next.js 16** (App Router, Cache Components, TypeScript strict) sebagai satu aplikasi: UI di `src/app`, REST API di `src/app/api/v1/*` dengan bentuk respons `{ success, data, meta?, error? }`, logika bisnis di `src/server/services/*`. API Next.js 16 berbeda dari versi sebelumnya; rujukan yang benar ada di `node_modules/next/dist/docs/`.
- **PWA:** `src/app/manifest.ts` dan service worker tulisan tangan `public/sw.js`. Service worker meng-cache halaman dan `GET /api/v1/orders/<id>`, sehingga tiket pengambilan (QR + kode 4 digit) tetap terbuka tanpa sinyal. Request `/api` lain, termasuk foto batch, selalu ke jaringan dan tidak pernah di-cache. Web Push memakai `web-push` dengan kunci VAPID.
- **UI:** Tailwind CSS v4, shadcn/ui (Radix), lucide-react, motion. Pembeli memakai layout mobile-first (`max-w-md`) yang melebar di desktop; mitra memakai sidebar desktop dan layout tablet kasir.
- **State:** TanStack Query v5 untuk data server, ditambah Server-Sent Events di `/api/v1/stream/batches` (pembeli) dan `/api/v1/stream/merchant` (mitra). State klien memakai zustand dengan persist (`src/stores/cart.ts`, `location.ts`, `tickets.ts`).
- **Database:** PostgreSQL 16+ dengan PostGIS, lewat Drizzle ORM (`casing: "snake_case"`) dan driver `pg`. Kolom `merchants.geom` di-generate dari latitude/longitude, jadi jangan pernah menulisnya. UUID memakai `gen_random_uuid()`. Akses server memakai `getDb()` dari `@/db`; script memakai `createDb()` dari `src/db/client.ts`.
- **Tanpa Redis.** Presensi pengguna aktif ada di tabel `customer_presence` dengan indeks GIST (`src/server/services/presence.ts`), kunci stok di `stock.ts`, dan job terjadwal di `npm run worker` (`scripts/worker.ts`, `src/server/jobs/`). `REDIS_URL` disiapkan untuk scaling nanti.
- **Peta dan QR:** Leaflet + react-leaflet dengan tile OpenStreetMap (`src/components/map/`), `qrcode.react` untuk QRIS dan tiket, `html5-qrcode` untuk pemindai.
- **Validasi dan waktu:** zod (kontrak di `src/lib/contracts`) dan react-hook-form. Semua waktu dalam WIB lewat `src/lib/time.ts`.
- **Pembayaran:** `PAYMENT_PROVIDER=simulator` membuat QRIS dinamis tersimulasi (format EMVCo + CRC16) dan webhook bertanda tangan HMAC-SHA512. Tombol "Simulasi Bayar" hanya untuk demo.
- **Login:** OTP lewat nomor HP (WhatsApp) atau email, sesi berupa cookie httpOnly `ss_session` (JWT). Pengiriman kode ada di `src/server/services/auth/otp-delivery.ts`: email lewat SMTP (`SMTP_USER` + `SMTP_PASS`, default Gmail `smtp.gmail.com:465` dengan sandi aplikasi, lewat `nodemailer` dengan timeout 10 detik dan satu transporter per proses; `nodemailer` ada di `serverExternalPackages`) atau Resend (`RESEND_API_KEY` + `OTP_EMAIL_FROM`, `fetch` biasa). Bila keduanya diisi, SMTP yang dipakai dan variabel Resend tidak dibaca. Pengirim SMTP selalu `"SMTP_FROM_NAME" <SMTP_USER>` karena Gmail menimpa alamat pengirim lain. WhatsApp lewat Fonnte (`FONNTE_TOKEN`, `fetch` biasa). Tiap penyedia aktif hanya bila variabelnya diisi; setengah pengaturan (mis. `SMTP_USER` tanpa `SMTP_PASS`) menjadi galat `Invalid environment variable …` dari getter-nya. Jalur yang dipanggil tiap request (`getRealOtpChannels()` untuk cek sesi, `configuredOtpProviders()` untuk permintaan kode) tidak pernah melempar galat itu: lewat `readOrFallback()` galatnya dicatat sekali ke log (nama variabel saja), kanal yang rusak tidak punya penyedia (permintaan kodenya dijawab `PROVIDER_CONFIG`, kanal lain tetap jalan), dan untuk cek sesi kanal itu tetap dihitung aktif supaya sesi dari mode demo tidak hidup lagi. `OTP_DEV_MODE=true` tidak mengirim apa pun dan menampilkan kode di layar (`dev_code`). Dengan `OTP_DEV_MODE=false`, kanal tanpa penyedia atau pengiriman yang gagal menjadi `503 OTP_DELIVERY_FAILED` (kode yang tidak terkirim langsung dinonaktifkan) dengan `details = { channel, reason, alternative_channel? }`. `reason` bernilai `PROVIDER_CONFIG` (key/sandi/pengirim/host salah, domain Resend belum diverifikasi, perangkat Fonnte terputus; pesannya tidak menyalahkan alamat pengguna dan menyarankan kanal lain bila tersedia, yang juga diisi di `alternative_channel` dan ditawarkan sebagai tombol di halaman login), `QUOTA` (batas kirim harian Gmail habis; kanal lain juga ditawarkan), `TEMPORARY` (timeout, gangguan penyedia, balasan SMTP 4xx) atau `RECIPIENT` (penyedia menolak alamat/nomor tujuan). Kode, token, sandi, isi balasan penyedia, dan alamat lengkap tidak pernah ditulis ke log (hanya penyedia, kode galat, dan tujuan yang disamarkan). `isRealOtpDelivery()` di `src/lib/env.ts` bernilai benar bila dev mode mati dan minimal satu penyedia aktif.

## Dynamic Discount Optimizer

`src/lib/pricing/dynamic-discount.ts` (fungsi murni) dan `src/server/services/escalation/` (worker). Optimizer ini aturan bertingkat, bukan model terlatih, sehingga langsung jalan untuk warung baru tanpa histori.

Input: sisa porsi, menit menuju `pickup_end_time`, jumlah pengguna aktif dalam 2 km selama 30 menit terakhir (`presence.countActiveUsersNear`), dan rasio konversi historis warung (default 0,65 untuk warung baru).

| Sisa waktu dan stok | Diskon aturan |
| :--- | :--- |
| ≤ 30 menit, ≥ 5 porsi | 70%, plus push "Diskon Kilat" ke pengguna terdekat sekali per batch |
| ≤ 30 menit, 1–4 porsi | 65% |
| ≤ 60 menit, ≥ 5 porsi | 60% |
| ≤ 90 menit, ≥ 8 porsi | 55% |
| selain itu | 50% (`DISCOUNT_BASELINE_PCT`) |

Setelah itu ada satu penyesuaian permintaan. Bila pengguna aktif kurang dari 0,8 × (3 × sisa porsi) dan konversi historis di bawah 0,5, diskon naik 5 poin (maks. `DISCOUNT_MAX_PCT` = 75%). Bila pengguna aktif lebih dari 2,5 × (3 × sisa porsi), konversi di atas 0,8, dan masih lebih dari 90 menit, diskon turun 5 poin (min. `DISCOUNT_MIN_PCT` = 40%).

Harga dibulatkan ke atas ke kelipatan Rp 500 dengan aritmetika integer, lalu `max(harga lantai, harga bulat)`. Karena pembulatan, diskon efektif bisa sedikit di bawah angka aturan (mis. 70% menjadi 69%), dan UI menampilkan angka efektif itu. Worker hanya boleh menaikkan diskon, dan setiap perubahan harga dicatat di `discount_adjustment_logs`.

## Surplus Prediction Engine

`src/server/services/prediction/` (sisi Node) dan `ml/` (Python).

- `ml/train_predict.py` melatih LightGBMRegressor dan LightGBMClassifier, lalu menulis prediksi 7 hari ke `merchant_surplus_predictions` dengan `model_version = 'lgbm-v1'`. Script ini dijalankan worker tiap minggu atau manual lewat `npm run ml:train`, tidak pernah di dalam request HTTP.
- Fitur: hari dalam minggu, akhir pekan, akhir bulan, malam Jumat, rata-rata surplus 4 minggu (per hari yang sama dan semua hari), tingkat habis terjual, konversi warung, kategori, harga, paket kejutan (selalu 0 untuk data seed dan menu baru karena paket kejutan sudah dihapus; kolomnya tetap ada untuk histori), dan **hujan malam hari** (`rain_evening_mm`: curah hujan pukul 17.00 sampai 22.59 WIB di lokasi warung dari Open-Meteo, data teramati untuk histori dan prakiraan untuk 7 hari ke depan, `ml/weather.py`). Kalau Open-Meteo tidak bisa diakses, fitur hujan kosong (NaN) dan training tetap jalan; `--no-weather` mematikannya. Prakiraan yang dipakai disimpan di `rain_forecast_mm` dan tampil di kartu perkiraan dasbor mitra.
- Pada data seed, fitur hujan belum membantu (hujan tidak memengaruhi surplus buatan, jadi ia hanya menambah noise). Manfaatnya baru bisa diukur dengan data uji coba nyata; jangan mengklaim cuaca meningkatkan akurasi sebelum itu.
- Dasbor dan `POST /api/v1/merchant/surplus/quote-ai` hanya membaca tabel itu. Bila belum ada baris, dipakai heuristik dari histori 4 minggu (`heuristic-v0`) yang diperbarui worker tiap hari tanpa menimpa baris `lgbm-v1`.
- Di UI, hasilnya ditulis dalam bahasa pemilik warung ("Sekitar 19 porsi kemungkinan belum laku…"), bukan nama model atau skor mentah.

## Pencarian lokasi dan checkout

**Radius 2 km** (`GET /api/v1/discover/nearby`, `src/server/services/discovery/`): selalu `ST_DWithin(geom, ST_MakePoint(lng, lat)::geography, meter)` yang diparameterisasi, memakai indeks GIST. Urutan default: Mitra Terverifikasi, lalu jarak, lalu diskon. Yang tampil hanya batch `ACTIVE` dengan `available_stock > 0` dan `pickup_end_time > NOW()` dari warung yang buka, dan bukan menu kejutan. Responsnya tidak di-cache karena foto batch bergantung pada siapa yang melihat (sesi akun demo juga melihat foto akun demo). Filter cepat di /discover ("< 500 m", "< 1 km", "Harga ≤ Rp 12.000", "Diskon ≥ 30%") berjalan di klien atas data radius yang sudah diambil (`applyQuickFilters`, `src/components/customer/lib/discover-sections.ts`), bukan parameter API, supaya patch SSE tetap menemukan batch yang baru masuk jangkauan. Section "Hampir Habis & Diskon Tertinggi" memuat batch yang tutup dalam 60 menit atau diskonnya ≥ 50%, dan "Harga ceban, maksimal Rp 12.000" mengurutkan yang termurah lebih dulu.

**Peta** dibuka dalam cakupan "Seluruh Indonesia" dari `GET /api/v1/discover/map-pins/all` (maks. `ALL_MAP_PINS_LIMIT`). Warung tanpa surplus live menjadi penanda abu-abu, penanda "hot" mulai diskon 50% dan "deal" mulai 30% (`src/components/map/types.ts`), dan penanda yang berdekatan dikelompokkan di zoom rendah (`src/components/map/cluster.ts`). Memilih lokasi lewat "Ambil di sekitar" mengubah peta ke cakupan radius (`src/stores/map-scope.ts`, tidak dipersist). Hanya kontrol pemilih yang memanggil `pickLocation()`; fix GPS di latar tidak mengubah cakupan.

**Verifikasi pengambilan** (`POST /api/v1/orders/:id/verify-pickup`), dalam satu transaksi:

1. pastikan status `READY_FOR_PICKUP` atau `PAID`, pesanan milik warung yang login, dan kode/QR cocok;
2. hitung dampak: pangan = Σ(jumlah × berat porsi), CO₂e = round(pangan × 2,5), uang hemat = subtotal normal − subtotal pemulihan + voucher;
3. set `COMPLETED` dan `picked_up_at`;
4. tambahkan `net_merchant_payout_idr` ke `merchants.wallet_balance_idr`;
5. tambahkan dampak dan poin ke profil pembeli; level naik dari Pemula ke Penyelamat (≥ 2 kg) dan Juara Pangan (≥ 5 kg). Enum di database tetap `SURPLUS_ROOKIE`/`SURPLUS_SAVER`/`SURPLUS_HERO`; labelnya di `BADGE_LABELS` (`src/components/customer/lib/format.ts`).

## Notifikasi Jam Lapar

Paling banyak satu push per perangkat per malam WIB saat warung dalam `HUNGER_ALERT_RADIUS_M` (500 m) dari titik pilihan pembeli (kos atau kampus) membuka diskon malam. Pembeli menyalakannya dari banner di /discover atau dari Akun/Dampak. `PUT /api/v1/push/hunger-alert` menyimpan langganan push perangkat beserta titik yang dibulatkan ke 3 desimal (sekitar 110 m) dan labelnya; mematikan menghapus titik itu. `POST /api/v1/push/hunger-alert/status` membaca status, dan `POST /api/v1/push/hunger-alert/test` ("Kirim contoh notifikasi") mengirim satu contoh hanya ke perangkat itu, sekali per `HUNGER_TEST_COOLDOWN_SECONDS` (60 detik); ini cara juri melihatnya bekerja. Datanya di kolom `hunger_alert_*` tabel `push_subscriptions` (indeks GIST parsial). Implementasi: `src/server/services/hunger-alert.ts`.

- **Per acara:** `notifyMerchantAudience` (publikasi, aktivasi batch terjadwal, Diskon Kilat) lebih dulu memanggil `sendHungerAlertsForMerchant`, hanya untuk warung uji coba yang buka dan hanya antara 20.00 dan `SURPLUS_WINDOW_END` WIB. Top-up, seed, dan publikasi warung demo tidak pernah memicunya, jadi mahasiswa sungguhan tidak dibangunkan oleh data fiktif. Perangkat yang baru menerima notifikasi ini dikeluarkan (`excludeIds`) dari push langganan dan push sekitar untuk acara yang sama.
- **Digest:** job kalender `hunger-hour` (`runHungerDigest`, 20.00–21.30 WIB) menghitung batch live dalam 500 m dari tiap perangkat yang belum dikabari malam itu. Selama `isDemoData()`, digest yang ikut menghitung warung bukan uji coba diawali "Data demo · ".
- **Sekali semalam:** perangkat diklaim lebih dulu lewat satu `UPDATE` bersyarat (`last_hunger_alert_on`), sehingga dua pemicu atau dua instance tidak mengirim dua kali. Klaim hanya terjadi bila kunci VAPID terpasang, jadi server tanpa push tidak menghabiskan jatah malam itu.
- **Tanpa WhatsApp:** teks WhatsApp hanya tampil sebagai pratinjau berlabel "Simulasi". Tidak ada jalur kirim, karena nomor Fonnte dipakai untuk OTP dan belum ada alur persetujuan.
- **Vercel:** `vercel.json` memanggil `/api/cron/tick` pukul 10.00 UTC dan 13.00 UTC. Di paket Hobby, cron 13.00 UTC jalan kapan saja antara 20.00 dan 20.59 WIB; tepat 20.00 butuh paket Pro atau scheduler luar yang memanggil `/api/cron/tick` dengan `CRON_SECRET`. Dengan `INLINE_JOBS=true`, trafik di endpoint ramai juga menjalankan job yang jatuh tempo. Pemicu per acara tidak bergantung pada cron.

## Alur kerja

- Butuh Node.js 22 atau lebih baru. Dengan Node 20, test gagal memuat ekstensi PostGIS di PGlite.
- Sebelum commit: `npm run typecheck && npm run lint && npm run test`. Untuk perubahan UI, jalankan juga `npm run test:e2e`.
- Mengubah skema: edit `src/db/schema.ts`, jalankan `npm run db:generate`, periksa SQL-nya (drizzle-kit memberi tanda kutip pada `geography(Point, 4326)`, hapus manual), lalu `npm run db:migrate`.
- Database lokal tanpa Docker: `npm run db:local` (PGlite + PostGIS, port 5433), pakai driver `pg`. PGlite hanya punya satu sesi Postgres untuk semua koneksi socket, sehingga koneksi paralel bisa saling menyela (`portal "" does not exist`, hasil kosong, bahkan statement asing di tengah transaksi). Karena itu `DB_POOL_MAX=1` dipakai untuk PGlite (`.env.example`, `npm run demo`, E2E). Web dan worker tetap dua proses, jadi sisa risiko itu masih ada di demo lokal. Uji rebutan stok yang benar-benar paralel butuh Postgres sungguhan (Docker atau Neon).
- Untuk melihat error server di balik test E2E yang gagal, jalankan dengan `E2E_SERVER_LOG=<file>`. Reset dengan `DROP SCHEMA` saat server jalan membuat cache PostGIS basi ("no spatial operator found"); jalankan ulang `db:local` atau hapus `.pglite/` saat server mati.
- Batch "malam ini" di data demo kedaluwarsa sekitar 2,5 jam setelah seed. Jalankan `npm run db:seed` (atau `npm run demo:reseed`) sebelum demo.
